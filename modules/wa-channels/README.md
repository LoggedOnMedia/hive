# WhatsApp Channel Poster (`wa-channels`)

Posts images, MP4 videos and/or text to the stores' WhatsApp Channels — now or on a
schedule — through [Whapi.Cloud](https://whapi.cloud), using one standard
WhatsApp number linked by QR code. Fully removable.

- **Regional manager:** posts to any channel or group, manages channels and
  groups, sees usage and every post.
- **Store manager:** posts only to the channel(s) linked to their own store,
  and sees deliveries to those channels.

## How it works

- `server/whapi.ts` is the **only** file that talks to the provider. Switching
  to WAHA / Evolution API / Wassenger means rewriting that file only.
- Posting creates a `wa_posts` row, its media in order (`wa_post_media`, up to
  10 JPEG/PNG/MP4 items, 16 MB each) and one `wa_post_targets` row per channel
  (groups are expanded and de-duplicated).
- Channels have no albums or carousels, so each media item is its own channel
  post, in order, 2 s apart, with the caption on the **last** one. A caption
  over 1,024 characters (WhatsApp's media-caption limit) goes as a separate
  text post after the media. `server/parts.ts` builds that list.
- Progress is saved after every part (`parts_sent`), so "Retry failed" carries
  on from where a channel stopped instead of re-sending.
- Sending happens in the background (`server/sender.ts`), **one channel at a
  time**, with a random gap (`WA_SEND_DELAY_SECONDS`, default 10–20 s) between
  sends. The database hands out targets and reserves send slots
  (`wa_claim_next`), so overlapping runs never double-send.
- A Supabase **pg_cron** job pings `/api/wa/tick` every minute (Vercel Hobby
  only allows daily crons). Each ping sends what fits in ~100 s (route `maxDuration` 120); "Post now" also
  starts a run immediately.
- Network failure: one retry. 4xx: no retry, marked failed. 429: back off
  10 min. **401: everything pauses** with "WhatsApp disconnected — re-scan the
  QR code", until the regional manager presses Resume.
- A send interrupted mid-request is marked failed, not resent (it may have
  reached WhatsApp) — check the channel, then "Retry failed".
- Times are stored in UTC and shown in Africa/Johannesburg.

## Sandbox (Phase 1) vs Premium (Phase 2)

`WA_PLAN=sandbox` enforces Whapi's free limits (whapi.cloud/price):

| Limit | Whapi | Hive blocks at |
|---|---|---|
| API requests / month | 1,000 | warns at 800, blocks at 980 |
| Messages / day (UTC) | 150 | 145 (every image/video/text part counts) |
| Active conversations / month | 5 | 5 channels posted to this month |

The 5-conversation limit means the Sandbox demo can reach **about 5 of the 22
channels a month**. Upgrading (Developer Premium, ~$29/month per number) is a
Whapi account change: set `WA_PLAN=premium` (and swap the token if it
changed). Usage is still logged and shown.

## Setup

1. Run `db/up.sql` in the Supabase SQL editor. (Installs from before a patch
   was added also need that `db/patch-*.sql`; fresh installs don't.)
2. From the Hive folder: `node modules/wa-channels/setup.mjs`
   - adds the `WA_*` settings (with a generated `WA_CRON_SECRET`) to `.env.local`
   - writes `db/schedule.local.sql` (git-ignored). Run it in the SQL editor —
     it enables pg_cron/pg_net, stores the secret in Vault and schedules the
     every-minute ping — then delete the file.
3. Paste the Whapi API token into `WA_API_TOKEN` in `.env.local`.
4. Add all `WA_*` variables to Vercel (**Secret**), redeploy.
5. In Hive: **WhatsApp → Channels → Sync channels**, link each channel to its
   store, then create groups (e.g. "All SUPERSPAR", "All TOPS").

## Configuration

| Variable | Meaning |
|---|---|
| `WA_CHANNELS_ENABLED` | `true` / `false` — the kill switch |
| `WA_API_TOKEN` | Whapi bearer token (server only) |
| `WA_API_BASE` | default `https://gate.whapi.cloud` |
| `WA_PLAN` | `sandbox` / `premium` |
| `WA_SEND_DELAY_SECONDS` | gap between channel posts, `min-max` or one number (default `10-20`) |
| `WA_CRON_SECRET` | shared with the Supabase cron job (generated by setup.mjs) |

## Touchpoints in the rest of Hive

Everything lives in this folder except these, each marked
`wa-channels module (removable)`:

1. `app/(app)/whatsapp/[[...slug]]/page.tsx` — one-line re-export (Next.js
   requires pages under `app/`).
2. `app/api/wa/[...path]/route.ts` — re-export + `maxDuration`.
3. `lib/nav.ts` — the "WhatsApp" nav item (tagged `feature: "wa"`).
4. `app/(app)/layout.tsx` — the line that switches the `"wa"` feature on when
   `WA_CHANNELS_ENABLED=true` (plus its import).
5. `proxy.ts` — `api/wa/` in the matcher exclusions, so the cron ping isn't
   redirected to sign-in.

When the flag is `false`: the nav item is hidden, `/whatsapp` and `/api/wa/*`
return 404, every action refuses, and cron pings do nothing.

## Removal

**Instant, reversible:** set `WA_CHANNELS_ENABLED=false` (and redeploy).

**Full removal:**

1. Delete this folder (`modules/wa-channels/`).
2. Delete `app/(app)/whatsapp/` and `app/api/wa/`.
3. Remove the nav item from `lib/nav.ts`, the `waEnabled` import and
   `features` line from `app/(app)/layout.tsx` (pass `features={[]}` or drop the
   prop), and `api/wa/|` from the matcher in `proxy.ts`.
4. Empty the `wa-media` bucket in Supabase Storage, then run `db/down.sql`
   (keep a copy before deleting the folder) — it drops the cron job, the Vault
   secret, all `wa_` tables and functions, and the bucket.
5. Remove the `WA_*` variables from `.env.local` and Vercel.

The generic `feature` support in `lib/nav.ts` and the shell can stay; with no
items tagged it changes nothing.

## Risks to share with the client

- **Unofficial integration.** Meta's official API doesn't support Channels.
  WhatsApp may restrict or ban the number — use a dedicated number, never a
  personal one.
- **Linked-device session can drop.** Keep the phone online and charged; when
  it drops, Hive pauses and asks for a QR re-scan.
- **Meta can change things without notice** and break this. The provider code
  is isolated in `server/whapi.ts` to keep that impact small.
